# ADR-043: Внедрение NATS JetStream как основы Event Mesh и брокера очередей сверхнизкой задержки

## Метаданные
- **Статус:** Approved (Утверждено)
- **Дата:** 2026-09-19
- **Авторы:** Архитектурный комитет, Инфра-агент
- **Утверждающие:** Иван Петров (Tech Lead), SecOps Lead, SRE Lead
- **Затрагиваемые сервисы:** Billing Service, Orders Service, API Gateway, Инфраструктурный кластер

---

## 1. Контекст
В микросервисной архитектуре корпоративного портала «МИРОВИЗОР» (ООО «Ромашка») реализован переход на паттерн распределённых саг (Saga Orchestration) для возвратов платежей и оформления заказов.

Исторический стек очередей (Apache Kafka) отлично справляется с долговременным накоплением больших объёмов событий (Big Data / Analytics). Однако при решении задач операционного взаимодействия микросервисов были зафиксированы следующие проблемы:
- **Задержка отклика (Latency):** Доставка сообщений в Kafka и коммит потребителей имеют задержку 4–12 мс, что замедляет сквозное время выполнения компенсаций саги.
- **Потребление ресурсов:** Брокер Kafka требует от 4 ГБ оперативной памяти и тяжелый Java/JVM рантайм.
- **Сложность Request-Reply:** Реализация синхронных вызовов между микросервисами требует организации временных топиков ответов и передачи корреляционных заголовков.
- **Отсутствие встроенного KV:** Сервисам приходилось разворачивать дополнительный Redis для хранения промежуточного состояния саги и параметров фиче-флагов.

---

## 2. Сравнительная матрица

| Критерий | Apache Kafka | NATS 2.10 + JetStream | Преимущество NATS |
| :--- | :--- | :--- | :--- |
| **Задержка P50 / P99** | 2.5 мс / 12.0 мс | **0.8 мс / 1.6 мс** | **~7x быстрее** |
| **Потребление RAM** | ~4096 МБ на ноду | **~42 МБ на ноду** | **~90x легче** |
| **Паттерн Request-Reply** | Имитация через временные топики | **Нативная поддержка `_INBOX`** | Встроенный RPC |
| **Встроенный Key-Value** | Требуется внешний Redis | **JetStream KV (`$KV.<bucket>`)** | Zero external dependencies |
| **Топология Subject** | Плоские топики | **Иерархические токены (`orders.*`, `billing.>`)** | Гибкая фильтрация |
| **Консенсус** | KRaft / ZooKeeper | **Встроенный Raft-консенсус** | Минимальный оверхед |

---

## 3. Принятое архитектурное решение
1. **Развернуть NATS JetStream в 3-узловой конфигурации** (Raft-кворум `nats-core-1`, `nats-core-2`, `nats-core-3`).
2. **Определить потоки JetStream:**
   - `ORDERS`: хранение событий жизненного цикла заказов (`orders.>`).
   - `BILLING_SAGAS`: очередь с политикой `workqueue` для шагов и компенсаций саги (`billing.saga.>`).
   - `AUDIT_LOGS`: аудит операций с ретеншном `limits` и маскированием PII (`audit.>`).
   - `PORTAL_EVENTS`: шина доменных событий портала (`portal.>`).
3. **Использовать JetStream KV:**
   - Бакет `saga-state` — хранение текущего статуса транзакций без внешнего Redis.
   - Бакет `system-config` — динамическое управление таймаутами и выключателями нагрузки.
4. **Интегрировать DomainEventBus:**
   - Все события доменной модели автоматически зеркалируются в топики `portal.events.<eventName>`.

## 4. Таксономия субъектов (Subject Hierarchy)
```
portal.
└── events.
    ├── OrderCreated
    ├── RefundInitiated
    └── SagaStepCompleted

orders.
└── v1.
    ├── created
    ├── payment_pending
    └── fulfilled

billing.
└── saga.
    ├── <sagaId>.start
    ├── <sagaId>.compensate
    └── <sagaId>.completed

audit.
├── billing.
└── security.
```

---

## 5. Последствия и риски
- **Позитивные:** Снижение P99 задержки координации саг до 1.6 мс, экономия до 85% оперативной памяти на брокерах, отсутствие необходимости в дополнительном Redis.
- **Риски и смягчение:** Требуется обучение команд разработке по модели NATS JetStream Consumer (AckPolicy, DeliverSubject). Для этого создан интерактивный пульт NATS Console прямо в портале.
